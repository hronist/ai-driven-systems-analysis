# Модуль 5: Распределенные системы и Асинхронная архитектура

Современный бэкенд редко состоит из одного монолита и синхронных REST API. Когда система растет, появляются микросервисы, очереди сообщений и распределенные транзакции. Аналитик должен уметь проектировать такие системы.

## 1. Event-Driven Architecture (Событийно-ориентированная архитектура)
Вместо того чтобы Сервис А вызывал Сервис Б (синхронно, ожидая ответа), Сервис А публикует **Событие (Event)** в брокер сообщений (Kafka, RabbitMQ, NATS). Сервис Б слушает этот брокер и реагирует на событие.

*   **Плюсы:** Слабая связность (Loose coupling). Если Сервис Б упал, Сервис А продолжит работать.
*   **Минусы:** Сложность отладки, eventual consistency (согласованность в конечном счете).
*   **Роль аналитика:** Описать контракты событий (Event Schema). Что именно лежит в JSON при событии `OrderCreated`? Как мы гарантируем, что схема события не сломает потребителей при обновлении (Schema Registry)?

## 2. AsyncAPI: Контракты для брокеров сообщений
Если для REST API мы используем OpenAPI (Swagger), то для событийной архитектуры стандартом является **AsyncAPI**.
Аналитик описывает:
*   **Channels (Топики/Очереди):** Куда мы пишем (например, `orders.events`).
*   **Publish/Subscribe:** Кто пишет в топик, а кто читает.
*   **Payload:** Структура сообщения (JSON Schema).

## 3. Паттерны распределенных транзакций
В монолите с PostgreSQL мы используем `BEGIN ... COMMIT`. В микросервисах так нельзя. Аналитик должен закладывать архитектурные паттерны в ТЗ:

### Saga Pattern (Сага)
Разбивает большую транзакцию на серию локальных.
*   **Хореография (Choreography):** Сервисы общаются через события без единого центра. (Сервис Заказов -> Сервис Оплаты -> Сервис Склада).
*   **Оркестрация (Orchestration):** Есть единый "Оркестратор", который командует сервисами.
*   *Важно для аналитика:* Обязательно спроектировать **Компенсирующие транзакции** (Что делать, если деньги списались, а на складе товара нет? Нужно вернуть деньги).

### Transactional Outbox (Паттерн Outbox)
Как гарантированно записать данные в свою БД и отправить событие в Kafka, чтобы ничего не потерялось при сбое?
*   Вместо прямой отправки в Kafka, сервис пишет событие в специальную таблицу `outbox` в своей же БД (в рамках одной транзакции с бизнес-данными).
*   Отдельный процесс (Relay) читает таблицу `outbox` и отправляет сообщения в Kafka.

## 🛠 Практическое задание
**Задача:** Спроектировать асинхронный процесс покупки курса.
1.  **Event Storming:** Выпиши 3 ключевых события (Events), которые происходят после того, как студент нажал "Оплатить". (Например: `PaymentProcessed`, `CourseAccessGranted`).
2.  **Архитектура Саги:** Опиши компенсирующую транзакцию. Что должно произойти, если `PaymentProcessed` успешен, но сервис выдачи доступов (`CourseAccessGranted`) упал с фатальной ошибкой?
3.  **Контракт:** Напиши черновой JSON-payload для события `PaymentProcessed`.
