# Модуль 6: Анатомия ТЗ (Структура документации)

Как собрать все артефакты (BPMN, Use Cases, ERD) в единый документ, который станет контрактом на разработку? 

## 1. Стандарты: ГОСТ 34 vs IEEE 830 vs PRD
*   **ГОСТ 34:** Тяжеловесный стандарт для гос. сектора.
*   **IEEE 830:** Классический западный стандарт Software Requirements Specification (SRS).
*   **PRD (Product Requirements Document):** Современный продуктовый стандарт (используется в Agile/Scrum).

Мы будем использовать гибридную структуру PRD/SRS, идеальную для коммерческой разработки.

### Альтернативы для разработчиков: ADR и RFC
В современных IT-компаниях (особенно в BigTech) классические ТЗ часто заменяют инженерными документами:
*   **ADR (Architecture Decision Record):** Короткий документ, фиксирующий одно важное техническое решение. (Например: "Почему мы выбрали PostgreSQL, а не MongoDB для аналитики"). Содержит Контекст, Решение и Последствия.
*   **RFC (Request for Comments):** Практика из мира Open Source. Инженер пишет документ с предложением новой архитектуры или фичи и отправляет команде на критику. После обсуждения RFC становится мини-ТЗ.

## 2. Обязательные разделы современного ТЗ

1.  **Введение и Бизнес-контекст:** Зачем мы это делаем? **Метрики успеха (Unit Economics):** Как мы поймем, что фича успешна? (Например, снижение CAC, рост ARPU или Retention). Глоссарий терминов.
2.  **Ролевая модель (RBAC/ABAC):** Кто имеет доступ к системе? Матрица прав доступа (CRUD для каждой роли).
3.  **Бизнес-процессы (AS-IS / TO-BE):** Вставка BPMN-схем с текстовым описанием.
4.  **Функциональные требования:**
    *   Список Use Cases (Основной, Альтернативные, Исключения).
    *   Бизнес-правила (Формулы, ограничения).
5.  **Требования к данным:**
    *   ER-диаграмма (Схема БД).
    *   Жизненные циклы сущностей (State Machines).
6.  **Интеграции и Интерфейсы:**
    *   Описание API (ссылка на Swagger/OpenAPI/AsyncAPI).
    *   Интеграции с внешними системами (Stripe, SendGrid).
7.  **Нефункциональные требования (NFR) и Feasibility:**
    *   Здесь мы не начинаем чек-лист NFR с нуля. Мы берем те ограничения (производительность, безопасность, SLA), которые выявили вместе со стейкхолдерами в Модуле 1, и детализируем их до конкретных метрик.
    *   **Feasibility (Анализ выполнимости):** Оценка стоимости инфраструктуры (AWS/GCP). Решение Build vs Buy (Пишем свой микросервис рассылок или покупаем SaaS?).
