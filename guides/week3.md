# Модуль 3: Пользовательские сценарии и Бэклог

Когда у нас есть бизнес-процесс (BPMN), нам нужно нарезать его на куски, которые можно отдать в разработку, не потеряв при этом общую картину.

## 1. User Story Mapping (Карта историй)
Бэклог в Jira — это плоский список. В нем легко потерять суть продукта. Джефф Паттон придумал User Story Mapping:
*   **Backbone (Хребет):** Шаги пользователя слева направо (Найти курс -> Оплатить -> Пройти -> Получить сертификат).
*   **Walking Skeleton (Шагающий скелет):** Самая тонкая версия продукта (MVP), которая позволяет пройти от начала до конца.
*   **Срезы (Releases):** Горизонтальные линии, отделяющие MVP от фич "на будущее".

### Приоритизация Бэклога
Аналитик должен уметь защищать MVP от "хотелок" бизнеса.
*   **MoSCoW:** Must have (Обязательно), Should have (Желательно), Could have (Можно), Won't have (Не в этот раз).
*   **RICE:** Reach (Охват) × Impact (Влияние) × Confidence (Уверенность) / Effort (Трудозатраты). Математический подход к выбору фич.

## 2. Быстрое прототипирование (Wireframing)
Разработчики часто мыслят таблицами БД, а заказчики — интерфейсами.
Прежде чем писать Use Case, набросайте черновой UI (в Figma, Balsamiq или Excalidraw). Часто именно на этапе рисования интерфейса всплывают скрытые бизнес-правила (Например: "А откуда на этом экране возьмется баланс пользователя?").

## 3. Use Cases (Сценарии использования)
User Story ("Я хочу оплатить курс") слишком мала для ТЗ. Use Case описывает **строгий алгоритм**.

**Структура Use Case для бэкендера:**
1.  **Предусловия:** (Токен валиден, курс существует). -> *Middleware в FastAPI.*
2.  **Основной поток:** Успешный сценарий.
3.  **Альтернативные потоки:** Пользователь ввел промокод. -> *Доп. ветка логики.*
4.  **Потоки исключений (Exception Flows):** Карта просрочена, БД недоступна. -> *Блоки try-except, HTTP 400/500.*
5.  **Постусловия:** Запись в БД создана.

### Альтернативы: Job Stories (JTBD) и CJM
*   **Job Stories (Jobs To Be Done):** Отличная замена классическим User Stories. Вместо ролей фокус идет на **контекст и мотивацию**. 
    *   *Формат:* `Когда [ситуация], я хочу [мотивация], чтобы [результат]`.
    *   *Пример:* «Когда я еду в метро с плохим интернетом (ситуация), я хочу скачать урок заранее (мотивация), чтобы учиться без прерываний (результат)». Это дает разработчику куда больше контекста (нужен оффлайн-режим и кэширование).
*   **CJM (Customer Journey Map):** UX-инструмент. Карта эмоций и точек контакта пользователя с продуктом. Аналитики используют её, чтобы найти "узкие места" (например, где пользователь злится из-за долгой загрузки).

## 🛠 Практическое задание
**Задача:** Фича "Применение промокода при покупке".
1.  **Story Mapping:** Выдели 3 шага (хребет) для процесса покупки и распиши под ними 2 релиза (MVP и V2).
2.  **Use Case:** Напиши подробный Use Case для применения промокода. Особое внимание удели **Потокам исключений** (промокод истек, промокод уже использован этим юзером, промокод не для этого курса).

## 🤖 ИИ-Ассистент (Проверка Use Case)
> «Вот мой Use Case для применения промокода. Мой стек: Python, PostgreSQL. Выступи в роли Senior Backend Developer. Проверь потоки исключений. Какие еще edge-кейсы я упустил с точки зрения конкурентных запросов (race conditions) и транзакционности БД?»
