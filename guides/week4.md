# Модуль 4: Системный дизайн: Данные и Интеграции

Аналитик в IT обязан говорить на языке данных и API. ТЗ без схемы данных и контрактов API — это просто сочинение.

## 1. Проектирование данных: ERD (Entity-Relationship Diagram)
Прежде чем писать модели SQLAlchemy/Django, аналитик проектирует ER-диаграмму.
*   **Сущности (Entities):** Таблицы (User, Course, Order).
*   **Атрибуты:** Поля (email, price, created_at).
*   **Связи (Relationships):** 1:1, 1:N, M:N.
*   *Важно:* Аналитик должен указать бизнес-ограничения (Constraints). Например, `email` должен быть уникальным, а `price` >= 0.

## 2. Визуализация API: Sequence Diagrams
Диаграмма последовательности (Mermaid) показывает, как системы общаются во времени.
*   Помогает выявить лишние запросы (проблема N+1).
*   Показывает, где логика синхронная (HTTP), а где асинхронная (Kafka/RabbitMQ/Celery).

## 3. Contract-First подход (OpenAPI/Swagger)
Современная аналитика включает проектирование API до написания кода.
Аналитик (или Lead Dev вместе с аналитиком) описывает эндпоинты, форматы запросов (JSON) и ответов в формате OpenAPI (Swagger). Это позволяет фронтендерам (TS) и бэкендерам (Python) работать параллельно.

### Альтернативы и дополнения к API-контрактам
*   **AsyncAPI:** Если ваша система общается через брокеры сообщений (Kafka, RabbitMQ, Redis Pub/Sub), OpenAPI не подойдет. AsyncAPI — это стандарт для описания асинхронных контрактов (какие ивенты мы паблишим, на какие подписываемся).
*   **gRPC / Protobuf:** Для высоконагруженных внутренних микросервисов. Контрактом выступает `.proto` файл, из которого автоматически генерируются классы для Python и TS.
*   **UML Class Diagram:** Альтернатива ER-диаграмме. Если ERD описывает таблицы в реляционной БД, то диаграмма классов описывает объекты в коде (ООП). Полезна, если вы используете NoSQL (MongoDB) или сложную бизнес-логику в памяти.

## 🛠 Практическое задание
**Задача:** Спроектировать модуль "Отзывы на курсы".
1.  **ERD:** Напиши Mermaid-код (тип `erDiagram`) для таблиц `Users`, `Courses`, `Reviews`. Укажи связи и типы данных (UUID, VARCHAR, INT).
2.  **Sequence Diagram:** Нарисуй процесс "Оставить отзыв". Участники: `Client (TS)` -> `API (FastAPI)` -> `DB (PostgreSQL)`. Учти проверку: "Купил ли юзер этот курс?".
3.  **API Contract:** Напиши пример JSON-запроса (Payload) для эндпоинта `POST /api/reviews` и пример JSON-ответа при ошибке валидации.
